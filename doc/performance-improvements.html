Customer screens — felt by everyone

3

Only read the reviews you need for star ratings

Where: the hotel home / discovery page, every time it loads
High impactModerate effort
Now

To show “★ 4.6 (3,000)” on each hotel card, the server loads every single review for every hotel on the page, then counts them and averages the scores. It throws almost all of that data away — it only needed the count and the average.

Reviews read just to show one rating3,000
After

Keep a small running tally on each hotel — a “sum of scores” and a “number of reviews.” When someone adds or removes a review, nudge those two numbers. The card then reads just two values, no matter how popular the hotel is.

convex/ratings.ts · getSummaries (lines 37–56)

// NOW — runs once per hotel on the page, reads all reviews each time
return await Promise.all(args.hotelIds.map(async (hotelId) => {
  const ratings = await ctx.db
    .query('hotelRatings')
    .withIndex('by_hotel_and_is_deleted', (q) =>
      q.eq('hotelId', hotelId).eq('isDeleted', false))
    .collect()            // <-- pulls in EVERY review
  const count = ratings.length
  const average = count === 0 ? 0
    : ratings.reduce((s, r) => s + r.rating, 0) / count
  return { hotelId, average, count }
}))

// AFTER — read a number kept up to date on the hotel itself
// (update hotel.ratingSum / hotel.ratingCount inside upsertRating & softDeleteRating)
return args.hotelIds.map((hotelId) => {
  const h = hotelsById.get(hotelId)
  return { hotelId, count: h.ratingCount, average: h.ratingSum / h.ratingCount }
})
Why it matters: this is the busiest screen in the app. Today it gets slower for everyone the more reviews a popular hotel collects. After the change, the home page loads at the same speed whether a hotel has 3 reviews or 30,000.

  .withIndex('by_is_deleted', (q) => q.eq('isDeleted', false))

Note: the photos themselves are already loaded lazily in the grid (good!). This fix is about the list request that happens before the grid even appears. It pairs naturally with #3 — if star ratings come back inside this same list, the separate ratings request disappears entirely.

Now

To work out “how full are we today,” the dashboard loads the entire booking history of every hotel — including stays from years ago that are long checked out — and then filters down to today in memory.

// NOW — load all holds + pending, filter by time in JS
const held = await ctx.db.query('bookings')
  .withIndex('by_status', (q) => q.eq('status', 'held')).collect()
const pending = await ctx.db.query('bookings')
  .withIndex('by_status', (q) => q.eq('status', 'pending_payment')).collect()
const expired = [...held, ...pending].filter((b) => b.holdExpiresAt < now)

// AFTER — use the by_hold_expires index to fetch only what's expired
const expired = await ctx.db.query('bookings')
  .withIndex('by_hold_expires', (q) => q.lt('holdExpiresAt', now))
  .collect()
Why it matters: users never see this job directly, but it competes with real booking writes every 15 minutes. Trimming it reduces the chance of it slowing down a checkout happening at the same moment.

Already fast — please leave these alone

A lot here is already done well. Worth knowing so these don't get “fixed” by accident:

Charts load only when neededRecharts is split into its own bundle, loaded lazily, and kept out of the first page download.
Routes are code-splitEach page ships as its own chunk (autoCodeSplitting), so you only download the screen you're on.
Animations are lightweightMotion uses the trimmed LazyMotion + m setup instead of the full library.
Hotel photos load lazilyCards use loading="lazy" with fixed width/height, so images don't block or shift the layout.
Hover pre-loadingHovering a hotel card quietly pre-fetches its detail page, so the click feels instant.
Long lists already paginateBookings and notifications use “load more,” and results are cached between components.
Availability is indexedThe room-availability check uses a single indexed lookup instead of one-per-room.
Unread count is cappedThe bell counts up to a limit instead of loading every notification to count them.

A sensible order to do them in

  1. #1 — Date-bound the dashboard occupancy scan. Biggest win, and it makes #2 easy. Pure backend change using an index that already exists.
  2. #2 — Combine the 6 dashboard queries into one. Smoother live updates and one database pass instead of six.
  3. #3 — Keep a running rating tally per hotel. Speeds up the busiest customer screen for good.
  4. #5 & #6 — Active-only rooms, map-based users. Quick backend wins on the two heaviest admin lists.
  5. #4 — Paginate the hotel list (fold ratings in). Do after #3 so the home page request returns everything in one shot.
  6. #7, #8, #9 — The easy cleanups. Small, safe, low-risk; good warm-up or fill-in tasks.
